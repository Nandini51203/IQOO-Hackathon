# RakshaSense — Person B: Check-in UI & Situation Card

Prototype module for the iQOO Hackathon 2026 build. This is **only** Person B's
piece of RakshaSense — it does not detect falls and does not send alerts.

## 1. What this module does

When a possible fall event is received, this module:

1. Shows an unmissable **"Are you okay?"** screen with a visible countdown.
2. If the user taps **"I'm OKAY"** in time → cancels the countdown, notifies
   the integration layer, returns to normal.
3. If the countdown reaches **zero** → notifies the integration layer that
   the user did not respond, then shows a **situation summary card**.

Person B never touches sensors, GPS, or SMS. It only exposes two callbacks
(`onTimeout`, `onConfirmSafe`) that the rest of the team wires up.

## 3. One-time setup: generate platform folders

This package ships the Dart side of the project (`pubspec.yaml` + `lib/`)
but **not** `android/`/`ios/` folders. That's intentional, not an
oversight: those folders are generated by the Flutter SDK and their exact
contents (Gradle/AGP/Kotlin versions, embedding files) depend on which
Flutter version is installed on your machine. Hand-writing them here,
without a Flutter SDK available to verify the build, risks shipping a
native scaffold that's silently mismatched with your toolchain — a build
error would look like a Person B bug when it's actually a version
mismatch.

Instead, generate them locally (safe — this does **not** overwrite the
existing `pubspec.yaml` or `lib/` files, it only fills in the missing
platform folders):

```bash
cd rakshasense_person_b
flutter create .
```

Then:

```bash
flutter pub get
flutter run
```

## 4. Test "Simulate Fall"

1. Run the app. You'll see a plain "Monitoring normally..." screen with a
   **Simulate Fall** button — this is a **development/testing trigger
   only**, standing in for Person A's real sensor callback.
2. Tap **Simulate Fall** → the check-in screen opens and the countdown
   starts (15s by default).
3. Either:
   - Tap **I'm OKAY** → screen closes, console logs `onConfirmSafe fired`.
   - Wait for the countdown to hit zero → console logs `onTimeout fired`,
     then the situation summary card appears.
4. Watch the debug console (the `flutter run` terminal, or your IDE's
   Debug Console) for lines prefixed `[Person B]` — that's the proof the
   callbacks fired correctly.

## 5. How the countdown works

- A single `Timer.periodic` ticks once per second (`check_in_screen.dart`).
- The duration is one constant: `CheckInConfig.countdownSeconds` (default
  `15`) in `lib/config/checkin_config.dart` — change it there only.
- A `_hasResponded` boolean guard ensures **exactly one** of
  `onTimeout()` / `onConfirmSafe()` ever fires, even under rapid taps or
  a tap that races the timer's last tick.
- `dispose()` always cancels the timer, so leaving the screen mid-countdown
  can't leave an orphaned timer running.

## 6. Integration contract (`onTimeout` / `onConfirmSafe`)

```dart
CheckInScreen(
  countdownSeconds: CheckInConfig.countdownSeconds,
  situationData: SituationData(situation: 'Fall detected', confidence: 'High'),
  onTimeout: () { /* Person C: EscalationManager.trigger(contact) */ },
  onConfirmSafe: () { /* Person A: resume monitoring */ },
)
```

Person B calls these callbacks and nothing else — it has no knowledge of
*how* escalation or "resume monitoring" work internally. In this repo
they're mocked with `debugPrint` in `home_screen.dart`.

```
Person A                 Person B                    Person C
FallDetector      →      CheckInScreen
                          ┌────────────┴────────────┐
                       I'm OKAY                   Timeout
                          │                           │
                          ▼                           ▼
                    onConfirmSafe()             onTimeout() → EscalationManager
```

## 8. Explicitly NOT implemented (by design, other people's modules)

- Accelerometer/gyroscope reading or any fall-detection algorithm (Person A)
- GPS/location lookup (Person C)
- SMS or phone calls (Person C)
- Emergency contact management (Person C)
- Volume-button gesture trigger, ambient sound classification, on-device
  LLM, dashboard, backend, or cloud services — out of scope for this
  prototype round entirely

The **"Confidence: High"** value on the situation card is a static
placeholder for this prototype round, **not** an ML-generated score.
`SituationData` is structured so a real confidence value, timestamp,
location, or trigger type can be plugged in later without changing the
widget.

## 9. Known Flutter/Android limitation

Flutter can keep the screen awake while the app is in the foreground
(via `wakelock_plus`, already wired into `check_in_screen.dart`), but it
cannot reliably wake the device from a locked/sleeping state or draw
over the lock screen — that needs native Android configuration
(`FLAG_SHOW_WHEN_LOCKED` / `FLAG_TURN_SCREEN_ON` set on the Activity, or
manifest changes) that lives outside Person B's Dart-only module. For
this prototype round, keep the phone unlocked and the app foregrounded
during the demo, as the original work-division doc's simplified scope
assumes.
